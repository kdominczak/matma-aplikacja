# Matma – aplikacja do matury z matematyki

Aplikacja mobilna do nauki: krótkie sesje, serie dni, ranking rozwiązanych zadań (bez XP).

## Stos
- Next.js 16 (App Router) + TypeScript + Tailwind CSS v4
- Capacitor 8 (Android/iOS) – pakuje folder `out/`
- KaTeX do wzorów – w treści pytań LaTeX w `$...$`, renderowany przez `src/components/ui/MathText.tsx`
- Backend: Supabase – ranking (`supabase/migrations`, klient `src/lib/supabase.ts` + `src/lib/ranking.ts`). Konto: anonimowe (ranking) albo e-mail + kod OTP (`src/lib/account.ts`; e-mail dopinany do anonimowego konta – to samo id). Ranking: nick + opcjonalne zdjęcie w Storage `avatars/<id>.jpg`. Ranking = poprawnie rozwiązane zadania, każde raz dziennie, najwyżej `ranking_daily_cap()` (150) dziennie (klucze są w aplikacji – pułap ogranicza skrypty; nie dodawaj limitu tempa w `record_answers`, zgubiłby kolejkę offline); odpowiedzi i serię zapisuje tylko `record_answers()` – serwer ocenia poprawność z `question_keys`, klient wysyła tylko literę (`src/lib/learning-sync.ts`). Nie dawaj klientowi uprawnień do kolumn serii. Kopia postępu (`user_progress`) i historia arkuszy (`exam_attempts`) – prywatne tabele z RLS, synchronizacja w `src/lib/cloud-sync.ts` (najpierw pobierz i scal przez `progress-merge.ts`, potem wysyłaj; nie wpływają na ranking). Kopię postępu zapisuje wyłącznie `save_progress(dane, oczekiwany updated_at)` – przy konflikcie (MA020) pobierz, scal, ponów; nie dawaj klientowi INSERT/UPDATE na `user_progress`. Kolejność migracji: pliki w `supabase/migrations` po kolei, seed `question_keys.sql` po drugiej
- Kod wspólny aplikacji i funkcji Deno: `supabase/functions/_shared/*.ts` (czysty TS, importy z rozszerzeniem `.ts` – stąd `allowImportingTsExtensions`)
- AI (korepetytor, wyjaśnienia, podpowiedzi): wyłącznie przez funkcję serwerową `supabase/functions/ai` (Deno – poza tsc/eslint) – klucz Groq tylko w sekretach Supabase, nigdy w aplikacji ani w `.env`. Klient `src/lib/ai.ts`, prompty `src/lib/ai-prompts.ts`, modele i `AI_ENABLED` w `src/lib/ai-config.ts` (`TEXT_MODEL`/`VISION_MODEL` zmieniaj razem z `ALLOWED_MODELS` w funkcji). Błąd Groq → 502 `upstream` + zwrot wiadomości (`refund_ai_quota()`, tylko `service_role`); wyczerpany limit → `AiLimitError` (pokaż drogę do `/premium`, nie zwykły błąd). Załączniki w korepetytorze (`src/lib/attachments.ts`): zdjęcia → JPEG ≤1280 px, PDF → tekst przez pdf.js na urządzeniu (skany jako obrazy); wiadomość z obrazem idzie do `VISION_MODEL` (Groq: max 3 obrazy na zapytanie)

## Ważne ograniczenie
`next.config.ts` ma `output: "export"`. Aplikacja działa bez serwera, więc NIE używamy:
Server Actions, Route Handlers z Request, `cookies()`, `headers()`, proxy, redirects/rewrites,
dynamicznych tras bez `generateStaticParams`. Dane z backendu pobieramy po stronie klienta.
API przeglądarki (`window`, `localStorage`, `navigator`) tylko w handlerach lub `useEffect`.

## Komendy
- `npm run dev` – podgląd w przeglądarce (http://localhost:3000)
- `npm run build` – static export do `out/`
- `npm run lint`
- `npm test` – Vitest: logika, treść zadań (KaTeX, klucze, punktacja, aktualność seeda) i migracje Supabase w PGlite (`tests/db/`). Po zmianie zadań, migracji lub logiki postępu testy muszą przechodzić
- `npm run blueprint:coverage` – ile różnych arkuszy w układzie prawdziwej matury da się złożyć z puli i gdzie brakuje zadań
- `npm run db:keys` – po zmianie zadań: generuje `supabase/seed/question_keys.sql` (klucze odpowiedzi dla serwera)
- `npm run mobile:sync` – build + kopiowanie do projektów natywnych
- `npm run android` – sync + otwarcie Android Studio

## Konwencje
- Komponenty: `src/components/<obszar>/` (quiz, gamification, ui)
- Wygląd: karta = klasa `card` (`@utility` w `globals.css`; odstępy p-4/p-5/p-6 dobiera widok, karta-link + `card-hover hover:border-brand/40`). Ładowanie: `src/components/ui/Skeleton.tsx` (`PageSkeleton` dla zakładek, `QuizSkeleton` dla ekranów pełnoekranowych) – nigdy `return null` podczas wczytywania
- Zrzuty ekranu: `npm run build`, potem `npm run screens` (Playwright, `e2e/screens.spec.ts`, dane ucznia w `e2e/fixtures.ts`) → `screenshots/` (telefon/komputer × jasny/ciemny × aktywny/nowy; na telefonie też kolejne ekrany po przewinięciu). Testy przepływów: `e2e/*.spec.ts` (`npx playwright test`)
- Nawigacja na telefonie: 5 zakładek (Ucz się, Zadania, Arkusze, Korepetytor, Profil); Wzory – przycisk w Zadaniach, Ranking/Odznaki/Błędy – skróty w Profilu, Ustawienia – w nagłówku
- Powitanie nowego ucznia: `src/components/onboarding/Welcome.tsx` (4 kroki, pokazywane, dopóki `needsPlacement`)
- Przypomnienia: `src/lib/reminders.ts` – lokalne powiadomienia na 7 dni naprzód, przeliczane przy każdej zmianie postępu (`useReminders` w AppShell); dziś pomijane, gdy uczeń już się uczył; `isExactNotification: false` (bez proszenia o alarmy dokładne). Ustawienia w `app-settings.ts` (`reminder`, `reminderAsked`), ikona `android/.../drawable/ic_stat_matma.xml`. Data matury: `src/lib/matura.ts`
- Brudnopis: `src/components/scratch/` (`ScratchBoard` w wersji inline/full, kalkulator); parser wyrażeń `src/lib/calc.ts` służy też do sprawdzania odpowiedzi w zadaniach otwartych
- Brudnopis – model obiektowy (`src/types/scratch.ts`, format 2): elementy z `id`, współrzędne w jednostkach kartki (1 = szerokość kartki). Figury i kąty liczy `src/lib/geometry/` (bez canvasa, testy w `tests/geometry.test.ts`); kąt przypięty zapisuje `{shapeId, vertex}`, a nie piksele. Scena (`scene.ts`): końce linii przypiętych do figur (`PointRef`), ramiona kąta w wierzchołku (boki + przypięte linie, `arms` = para "v:<i>"/"l:<id>"). Magnes: `src/lib/geometry/snap.ts`. Bryły: `src/lib/geometry/solids.ts` – wielościany w 3D (ściany), rzut ukośny gabinetowy, krawędzie niewidoczne liczone ze ścian (nie wpisuj ich ręcznie); bryły obrotowe opisane w pudełku z elipsami. Wierzchołki brył działają jak figur płaskich (`shapeVertices`, `vertexNeighbors`). Oznaczenia boków (`MarkItem`: długość, znaczniki |/||/|||, środek) przypięte do boku/krawędzi/linii (`EdgeRef`); podpis rysowany jako KaTeX nad canvasem (`labelToTex` w `src/lib/geometry/marks.ts`). Wysokość = linia z `toRef: {foot: [wierzchołek, bok]}` – spodek prostopadłej liczony na bieżąco. Rysowanie: `scratch-draw.ts` (warstwy: pismo → figury → linie → kąty). Widok (`View`: przybliżenie 40–250% + przesunięcie) to tylko transformacja płótna i tła (`withView`, `ScratchBackground` z `zoom`/`pan`) – model notatek się nie zmienia; tolerancje dotyku dziel przez `Z` (z przybliżeniem), nie `W`. Dwa palce = szczypanie/przesuwanie, narzędzie „Przesuń”, Ctrl+kółko. Pełny ekran = szuflada o zmiennej wysokości (`scratch.sheetHeight` w localStorage). Notatki zapisuje `src/lib/scratch-notes.ts` (ostatnie 40 zadań; w arkuszu klucz z czasem rozpoczęcia podejścia)
- Lekcje: każdy z 25 działów ma pełną lekcję w `src/data/topics/<id>.ts` (teoria w krokach z przykładami – kroki rozwiązania rozdziela `\n`, wykresy z `guides` na linie pomocnicze – wzory, haczyki, zadania zamknięte w `tests` na 3 poziomach trudności, zadania otwarte). Widok lekcji: Teoria / Wzory / Zadania – bez testów do zaliczania, serc i kłódek (decyzja z 29.10.2026). Krok teorii może mieć `check` (pytanie zaraz po kroku; standard lekcji i wzór: `docs/lekcje.md`, `funkcja-kwadratowa.ts`), koniec teorii to „Sprawdź, czy rozumiesz” (`InlineCheck`, zapis `saveLessonCheck` – statystyki bez zaliczania testu). Postęp działu = zadania rozwiązane w całości (`topicTaskProgress`), odznaki – poziomy opanowane w zadaniach (`masteredLevels`, ≥ 75%); `progress.tests` już tylko czytamy (stare zapisy, test na start). Nie zmieniaj id istniejących zadań (klucze serwera, Pudełko porażek, zamrożone arkusze); nowe zadanie zamknięte → `npm run db:keys`. Odpowiedzi ABCD są mieszane tylko na ekranie (`src/lib/options.ts`) – w danych litera zostaje, więc nie odwołuj się w treści do „odpowiedzi A”
- Zakładka „Zadania”: dwa widoki (`?widok=lekcje` w adresie): zadania z działów i ścieżka lekcji (`src/components/topic/LearningPath.tsx`, według celu ucznia). Wszystkie działy odblokowane; zadania z testów i `openTasks` lekcji + warianty z szablonów (`src/data/practice/` – mechanizm dla działu bez lekcji, obecnie pusty). „Rozwiązane” liczy się tylko z wyniku sprawdzonego przez aplikację, samoocena nie
- Ekran główny (`src/components/home/Dashboard.tsx`) – tylko plan na dziś, „wróć do…”, wejście do lekcji, szacowany wynik i seria. Czas nauki, odznaki, Pudełko porażek – w Profilu; nie dokładaj tu kolejnych kart
- Ustawienia lokalne (imię, zdjęcie, wibracje, dźwięki, konfetti): `src/lib/app-settings.ts`
- Premium, limit AI, kody poleceń i zakupy (`docs/premium.md`): stan liczy tylko serwer (migracje `20261102120000_premium_referrals.sql`, `20261104120000_purchases.sql`; funkcje `consume_ai_quota`, `redeem_referral`, `grant_premium`, `set_purchase_premium`), aplikacja czyta go przez `account_status()` w `src/lib/premium.ts` – nigdy nie naliczaj Premium ani limitu lokalnie. Zakupy: Google Play przez RevenueCat (`src/lib/purchases.ts`, plugin ładowany tylko na Androidzie z `NEXT_PUBLIC_REVENUECAT_ANDROID_KEY`); zakup tylko na koncie z e-mailem, SDK zalogowane na id konta Supabase. Funkcja `supabase/functions/revenuecat`: webhook + synchronizacja po zakupie → `set_purchase_premium()` (kolumna `purchase_until` nadpisywana stanem z API RevenueCat; dni z poleceń w `premium_until` się sumują), czysta logika w `supabase/functions/_shared/purchase.ts` (testy `tests/purchase.test.ts`, klient – `tests/purchases-client.test.ts`). Limit 5 wiadomości: SQL `ai_free_daily_limit()` i `AI_FREE_DAILY_LIMIT` zmieniaj razem. Lejek: `trackFunnel()` (`src/lib/funnel.ts`) → `funnel_events`, raport `supabase/admin/lejek.sql`; nowy krok = check w tabeli + lista w `track_funnel()` + typ `FunnelStep`
- Cel ucznia (`src/lib/goal.ts`, suwak `GoalSlider` w powitaniu i ustawieniach): punkty 15–50, zapisywane jako procent w `progress.target` (dawne 30/60/85 działają). Działy potrzebne do celu wylicza `topicsForGoal()` z wag na maturze (najwięcej punktów za godzinę nauki, 80% wagi z opanowanego działu) – korzystają z tego plan, wyzwanie dnia i ścieżka lekcji; nie wracaj do stałych grup „na 30/60/85%” (`topic.target` to już tylko grupa „fundamentów” dla odznaki). Test na start nie nadpisuje celu – tylko podpowiada
- Plan na dziś (`/plan`, `src/lib/planner.ts`): powtórki w odstępach (`src/lib/reviews.ts`, pudełka 1/3/7/14/30 dni) + dział o największym zysku punktów (waga działu × brak opanowania) + 2 zadania z innego działu. Bez AI, liczony na urządzeniu, stały w ciągu dnia (ziarno = dzień + runda)
- Moderacja nicków: `src/lib/moderation.ts` i ta sama lista w SQL (`nick_allowed()`); test pilnuje zgodności – zmieniaj obie naraz
- Usuwanie konta: `src/lib/delete-account.ts` + `delete_my_account()` (kaskada od `auth.users`). Polityka prywatności `/prywatnosc` i strona usuwania konta dla Google Play `/usun-konto` (dane w `src/data/legal.ts`); zgłoszenia mailowe – procedura SQL w `supabase/admin/usun-konto.sql`
- Arkusze w trybie egzaminu: dane `src/data/exams.ts` (próbne z zadań aplikacji; oficjalne CKE tylko przepisane z PDF + klucz, nigdy z pamięci), logika `src/lib/exam.ts`, widoki `src/components/exam/`, trasa `/arkusz/[examId]`. Po „Zakończ” (czas stoi, `session.finishedAt`) zadania otwarte rozszerzone bez poprawnego wyniku ocenia się krokami ze schematu (`ExamAssessment`, `applyAssessment` obcina punkty do schematu) – status `partial`, nigdy `correct`; próba zapisuje się dopiero po sprawdzeniu (w chmurze `exam_attempts` jest tylko do dopisywania). Ocena ze zdjęcia (Premium, `PhotoGrading`): `transcribeSolution` → uczeń poprawia tekst → `gradeSolution`; prompty i modele w `supabase/functions/_shared/` (serwer narzuca je przy `purpose`), osobny licznik `consume_grading_quota` (`docs/ocenianie-ai.md`); zmiana promptu = `npm run grading:eval` przed i po
- Szablony arkuszy (`src/data/blueprints.ts`): układy prawdziwych matur podstawowych z „Zasad oceniania” CKE – pozycja, punkty, typ (`abcd`/`truefalse`/`choice`/`short`/`extended`), dział podstawy I–XIII. Od 2025: 50 pkt (wcześniej 46). Tylko struktura, bez treści zadań CKE. Metadane zadań do składania arkuszy: `src/data/task-meta.ts` (dział z `topic.section`, wyjątki w `TASK_OVERRIDES`)
- Arkusze próbne są zamrożone w `src/data/mock-exams.ts` (listy id zadań) – nowe zadania w puli ich nie zmieniają; nie usuwaj zadań, które w nich są. Świadoma wymiana arkuszy: `npm run exams:freeze`. Kody arkuszy losowych odtwarzają ten sam arkusz tylko przy tej samej puli zadań
- Generator arkuszy (`src/lib/exam-generator.ts`): wypełnia pozycje szablonu zadaniami z puli, z drabiną zastępstw (typ → pokrewny dział → rozbicie otwartego → dowolny dział → brak), każde zastępstwo zapisane i pokazane uczniowi. Kod arkusza = rok układu + ziarno (np. `26k3f9a`), arkusz losowy ma id `los-<kod>` i stronę `/arkusz/losowy/?kod=`. Wagi działów na maturze (50 pkt) – `src/lib/exam-weights.ts`, liczone z szablonów, nie wpisywane ręcznie
- Szacowany wynik (`src/lib/estimate.ts`): Σ punkty działu na maturze × oczekiwany odsetek punktów (`expectedScore` w `src/lib/mastery.ts` – ostrożna skuteczność ze wszystkich zadań + zaliczone testy). Wykres odtwarzany z dziennej historii `statsByDay` (sumy = `topicStats`). Każda odpowiedź do statystyk działu idzie przez `countAnswer()` w `src/lib/progress.ts`; samoocena zadań otwartych nie liczy się jako poprawna
- Szablony parametryczne zadań: `src/data/templates/` (rejestr w `index.ts`, poradnik `docs/szablony-zadan.md`). Warianty mają stałe id `<szablon>-<n>` – nie zmieniaj id ani kolejności istniejących szablonów. Każdy szablon ma sprawdzenie siłowe w `tests/templates.test.ts`
- Typy: `src/types/`, logika: `src/lib/`, dane testowe: `src/data/`
- Teksty UI po polsku
